# Long-horizon execution: continuous productive progress

## Objective

Maximize scientific correctness, completeness, robustness, reproducibility and useful progress. Calendar duration is not an optimization target or a required minimum. Continue for days or weeks where meaningful work remains. Do not manufacture delay, run pointless repeated reviews, or stop solely because a minimal pipeline produced output.

Develop a complete vertical slice early, release its interim artifacts, and harden it while maintaining a working incumbent. Keep the next useful independent task running when another job waits for a download, model inference, access decision, or validation. Do not consume reasoning tokens repeatedly checking healthy long-running jobs.

## Reasoning and account capacity

Use the user's selected GPT-6 Astra High setting as the starting preference for substantive work, if available. Keep scientific design, interpretation and difficult integration on strong Codex agents. Use Extra High/Max for high-leverage decisions and independent acceptance review when the supported configuration and allowance permit. Ultra is excluded. Prefer Standard speed; do not pay for Fast mode merely to reduce elapsed time.

Read the actual installed controls and verify effective settings. UI names are preferences, not guessed API enum values. Do not modify global client settings for unrelated chats. If a requested level is not available, report the actual configuration and keep useful work moving at the selected permitted setting rather than claiming a change.

Use observed allowance/reset information only when exposed through supported interfaces. Do not reverse-engineer account storage. Sample usage at meaningful boundaries rather than after every command. Reduce redundant context, repeated reviews and counterproductive parallelism first. Do not silently downgrade important scientific work or route it to external agents to appear continuously active.

When provider capacity is exhausted: preserve work, record `WAITING_FOR_CAPACITY`, record a reset time only if known, keep safe deterministic jobs running, and resume through an actually supported scheduler/controller once capacity returns. A reset-time guess is not a reliable schedule. Do not buy credits or switch to paid API credentials without a separately approved budget.

Development-agent use and runtime inference are separate. The completed app must have its own legitimate backend as specified in file 16; Codex's development allowance is not a free general-purpose inference service for the application.

## Productive job management

Use scoped task contracts and long enough deadlines for measured workloads. Distinguish network retries, controller timeouts, code defects, slow valid computation, and model stalls. Process liveness, job counters, output changes, resource use and dependency state inform diagnosis; one old log timestamp does not justify terminating work.

Use durable event-driven/job-completion notifications where possible. Otherwise use an inexpensive deterministic poller with adaptive intervals. An hourly model supervisor is recovery insurance, not the normal execution engine. Its healthy checks should be small and quiet; even a silent model invocation can consume usage.

Do not build a second elaborate orchestration product. Start with the simplest durable queue, ownership/lease mechanism, stage cache and process controller that passes recovery tests. Expand only when actual failures show the need. Planning and observability support implementation, not replace it.

## Iteration contract

Every central worker gets at least two substantive evaluation/refinement passes. Across the full system execute at least three distinct integration rounds: initial real pipeline, corrected/expanded scientific pipeline, and hardening with independent challenge. A documented no-change verdict counts only when new executed evaluation supports it; arbitrary edits are not required.

For a candidate change record: failure or improvement objective; affected artifacts/versions; evaluation split; measured before/after; regressions; acceptance or rejection; next action. Prioritize wrong scientific conclusions and data corruption before cosmetic cleanup or micro-optimization. Compare component ablations when they can distinguish whether a complicated feature helps.

Keep a best validated incumbent. A speculative improvement must not overwrite it before tests pass. Use rollback/promotion rather than restarting all prior acquisition or relabeling failures as missing data.

## Stop and pause semantics

`FUNCTIONAL_ALPHA_AVAILABLE` is an interim product milestone. It does not complete this assignment. Final completion requires the expanded hardened-alpha gates, minimum substantive review, a real delivery package, and diminishing useful returns.

Before tuning, choose material-improvement criteria appropriate to the pilot. Two consecutive development rounds with no material gain, all required gates passing, and no high-severity issue justify final untouched-holdout and independent validation. Use the remaining effort to fix actual acceptance defects, not to invent new scientific scope. If a fresh holdout failure is used for training/repair, relabel it development evidence and obtain a new untouched holdout.

User pause/stop is authoritative. The supervisor must not interpret an intentional pause as a stall. Essential unresolved permissions, spending, source authority, or scientific scope decisions can require user input; continue unrelated unblocked work. Ordinary engineering choices, optional donor failures, and absence of expert labels do not require abandoning the build.

A session ending is not project completion. Checkpoint first when possible; if forcibly interrupted, resume from validated durable artifacts. Never claim a job is running without actual process/controller evidence.
