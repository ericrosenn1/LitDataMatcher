# Interim results and completion visibility

The user accepts a build lasting days or weeks but wants useful results during sustained execution. These are progress checkpoints, not deadlines, promises, source-selection biases, or a reason to reduce scientific acceptance criteria.

## Early working slice

As soon as the first real slice works, expose its report and run command while continuing development. Prefer a modest complete question-data-evidence path over ten elaborate unconnected modules. Maintain the best working version while improving candidates in isolated branches/worktrees.

## Around one week of productive operation

Expose a real literature corpus and at least one real dataset path; typed claims/questions/requirements; sample-backed capabilities; one auditable match or correctly explained no-match outcome; external evidence integration progress; and executed tests. Clearly distinguish real outputs from fixtures and pending capabilities. If this is achieved earlier, deliver it earlier rather than waiting seven days.

## Around two weeks of productive operation

Expose the expanded cross-source/cross-context evaluation, multiple dossiers, worker error reductions, integrated refinement, recovery/offline checks and the current alpha acceptance status. A calendar date does not prove progress. State capacity/access wait periods separately from actual execution and do not make up elapsed compute time.

## Notification policy

The ordinary controller records concise progress locally and at meaningful Git checkpoints. The scheduled supervisor is not a periodic prose reporter. Surface a message at a functional milestone, substantial hardening result, consequential intervention, required user decision or final delivery. A week checkpoint can summarize concrete usable artifacts and measured changes without narrating every activity.

A meaningful progress update contains: usable output path and command; data coverage; current acceptance state; actual tests and principal remaining defects; next high-value work; and whether anything requires user action. Avoid assurances such as 'still working' unsupported by live job evidence.

## Final stop

Do not stop after the first functional CLI/report. Do not continue indefinitely after the hardened-alpha gates and diminishing-return closeout pass. Deliver the current version and optional future backlog, stop new build jobs, preserve safe completed outputs, and disable or idle the project supervisor. Manual user pause/stop always takes precedence.
